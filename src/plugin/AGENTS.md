## Purpose
The JUCE shell around the core. `PsyBoxProcessor` builds the APVTS from `paramDefs()`, converts JUCE MIDI to `psy::MidiEvent`, runs `psy::Engine`, and owns the message-thread features: generator, locks, undo/redo history, presets, state save, macro names and the modulation API the knobs use. `PsyBoxEditor` is a fixed 1280×820 logical canvas scaled as a whole, and the drag-and-drop container for mod sources.

## For AI Agents

### Working In This Directory
- **Thread split.** `processBlock` is the audio thread: relaxed atomic loads, no allocation (MIDI events only `push_back` within reserved capacity). Generator, presets, history and locks are message-thread only. The UI reaches the audio thread only through APVTS, the atomics (`scope`, `outPeak`, `outMeanSquare`, `compMeters`, `arpStep`, `lastPlayedNote`, `lastBpm`) and the `ModView` behind a `SpinLock` the audio thread only try-locks. MIDI: CC 120/123 are tested before other controllers (they are controllers too); controllers never take the last quarter of the reserved event space, so note events always fit.
- Generate (`generateWithSeed`), Mutate and `generateArpPattern` run `psy::levelPatch` on the new patch before `applyState`, so every patch lands on one loudness (Level, `P::PatchGain`; a locked Level stays). Loading presets, sessions or history never re-levels.
- **Patch swaps.** Every swap (Generate, Mutate, undo/redo, presets, init, category switch, a host `setStateInformation`, a new playback key) holds a `PatchChange` (RAII, nests) around its `applyState`. `processBlock` fades the old sound out over 10 ms on the old values, stays silent while `openChanges > 0` (at most a second), then `engine.reset()` and replays what sounded with a ~2.7 ms fade-in: the sustain pedal, the held keys and the keys the pedal held (let go again). Kicks replay the held keys too (no pedal, no fade-in): holding a key and pressing Generate plays every new sound. In a DAW that only works because the latency never moves (`Engine::latencySamples`): a VST3 host answers a latency change with `setActive (false/true)`, `prepareToPlay` clears the held keys, and the note was lost on every patch with a different distortion setting (2026-10-24; `heldKeyPlaysEveryNewSound` restarts the bench like such a host). Fade lengths follow the sample rate. A block reads the parameters, then checks the epoch again: a change that opened meanwhile fades out on the old values. A change during the fade-in fades out from the current gain. Generate and Mutate compute and level the patch (50-140 ms) *before* opening the change, so the old sound plays on meanwhile. Before 2026-10-17 the restart came after the 10 ms fade regardless, played the old patch again and took the new values mid-note.
- Applying a generated patch goes through `applyState`, which sets APVTS params so the host sees changes. It also enforces the family (`withGlobals`, static so the batch shares it): `EngineMode` from the category, the current Volume and qualities, and `ArpOn` off where `hasArp(category)` is false (basses, kicks, energy; `normaliseFamily` does the same after a state load). Then `pushHistory` and a change broadcast.
- **Playback key** (`setPlayKey`, `playKey`/`playOctave` on the message thread, `playNote` atomic, saved in the session as `playKey`/`playOctave`, not in presets). The audio thread takes `playNote` into `mapTo` only at `prepareToPlay` and at a swap's `engine.reset()` (a change opens a `PatchChange`), so the keys never switch notes mid-sound. With `mapTo` set, each note-on plays `mapTo` (a doubled note-on retriggers, the engine keeps one stack entry) and a note-off only goes out when no key is held; `heldVelocity`/`pedalHeld` stay per physical key and the restart replays them as `mapTo`. `bounceRequest` renders `playNote` when set.
- **Batch** (`startBatch`, `cancelBatch`, `getBatchStatus`, `getBatchFiles`, `getBatchFolder`, `batchCount` saved as `batchCount`). `BatchJob` (pimpl): a `juce::ThreadPool` of low-priority threads (CPUs − 2, 1..8), one job per sound working on copies taken at the start (category, state, locks, Arp/Tune toggles, tempo, note): a local `Generator`, `levelPatch`, `withGlobals`, `makeBounce`, `renderBounce` into `Bounces/<Category> batch <time>/NN <Category> <SEED> <note>.wav` (no `#`: `createLegalFileName` drops it). Each sound's `progress` and `state` are atomics (the file is set before `state` is released). Destroying the job sets `cancelled` and waits; the renders check it every block. Start/cancel broadcast a change so every window shows it.
- Generate clears typed macro names (the new macros are named automatically); undo/redo and category slots carry them. Older sessions stored "Macro N" for untouched names; `readMacroNames` treats that as automatic.
- State/preset loading maps by param **id** via `findParam`. Unknown ids are ignored, missing ones keep defaults. Keep that tolerance.
- Both files are also compiled into `psybox_snapshot` (it defines `JucePlugin_Name` itself). Don't depend on plugin-wrapper-only macros without a fallback.

### Testing Requirements
- `PSYSNAP_PLUGINTEST=1 ./build/psybox_snapshot_artefacts/Release/psybox_snapshot` runs `tools/ProcessorTest.cpp`: deterministic checks of swaps (host state load without a step, CC 123, sustain, bypass), MIDI floods, the global settings undo/init keep, redo keeping tweaks, slot macro names across a session, offline latency at prepare and the tail. It must print only PASS lines. For anything else, build the plugin target and check in the Standalone app.
- If you touch state save/load: save a preset, reload, and confirm locks, seed and category survive.
